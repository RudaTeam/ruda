# ADR-0002: Rust и структура Cargo workspace

- **Статус:** Принято
- **Дата:** 2026-09-30
- **Связанные ADR:** 0003, 0004, 0006, 0013

## Контекст

Язык задан требованиями — Rust. Нужно организовать код так, чтобы:

- выделенный сервер собирался без графики, окна и звука: быстро, без GPU-зависимостей, на любом headless-железе;
- клиент и сервер использовали *один и тот же* код физики и правил, иначе предсказание движения на клиенте разойдётся с сервером;
- время компиляции оставалось терпимым по мере роста проекта;
- границы модулей проверял компилятор, а не договорённости.

## Решение

**Тулчейн.** Rust stable, edition 2024. Версия закреплена в `rust-toolchain.toml` и обновляется
осознанно, отдельным коммитом.

**Workspace.** Виртуальный манифест (`resolver = "3"`), у всех крейтов `publish = false` (ADR-0003).
Стартовая раскладка:

```text
ruda/
├── crates/
│   ├── ruda_core       # координаты, ResourceId, реестры, общие типы
│   ├── ruda_world      # чанки, палитры, освещение, доступ к блокам
│   ├── ruda_worldgen   # генерация мира
│   ├── ruda_storage    # сохранение мира на диск
│   ├── ruda_sim        # общая симуляция клиента и сервера: движение, коллизии, правила взаимодействия
│   ├── ruda_protocol   # сообщения протокола и кодек
│   ├── ruda_net        # транспорт: QUIC и in-memory
│   ├── ruda_server     # авторитарный игровой сервер
│   ├── ruda_client     # клиентская логика: кэш мира, предсказание, интерполяция
│   ├── ruda_render     # рендер на wgpu, мешинг
│   ├── ruda_input      # абстракция ввода
│   ├── ruda_ui         # игровой интерфейс
│   └── ruda_audio      # звук
├── content/
│   └── base/           # базовая игра (ADR-0013)
├── apps/
│   ├── ruda/           # клиент + встроенный сервер
│   └── ruda-server/    # выделенный сервер
├── tools/              # упаковка ассетов, бенчмарки, утилиты
└── docs/
```

Раскладка стартовая: крейты можно делить и объединять. Правила ниже менять нельзя.

**Правила зависимостей:**
- `ruda_server` и всё, от чего он зависит, не тянет `wgpu`, `winit` и аудио. Это проверяет CI через `cargo-deny`: секция `[bans]` с `wrappers` разрешает `wgpu` только в `ruda_render`, а `winit` — только в `ruda_render`, `ruda_input` и `apps/ruda`.
- Физика и правила, нужные и клиенту, и серверу, живут только в `ruda_sim`. Дублировать их в `ruda_client` запрещено.
- `content/base` использует только публичный API движка (ADR-0013).

**Профили сборки:**
- `dev`: свои крейты собираются с `opt-level = 1`, зависимости — с `opt-level = 3` (`[profile.dev.package."*"]`). Иначе в debug-сборке играть невозможно.
- `release`: `lto = "thin"`, для ежедневной проверки производительности.
- `dist`: наследует `release`, плюс `lto = "fat"` и `codegen-units = 1`. Для сборок, которые выпускаем.
- Везде `panic = "unwind"`: если встроенный сервер паникует, клиент должен показать экран ошибки, а не упасть.

**Качество:** на каждый PR — `rustfmt`, `clippy -D warnings`, `cargo-deny` (лицензии, бан-лист, уязвимости)
и тесты. Логирование и профилирование идут через `tracing`; интеграция с Tracy — за feature-флагом.

## Последствия

**Плюсы:**
- Граница «сервер без графики» проверяется автоматически.
- Клиент предсказывает движение тем же кодом, что исполняет сервер.
- Крейты компилируются параллельно и инкрементально.

**Минусы и риски:**
- Много крейтов — больше `Cargo.toml` и церемоний с видимостью API.
- Если крейты нарежем неудачно, код придётся переносить. Это допустимо: раскладка явно стартовая.
