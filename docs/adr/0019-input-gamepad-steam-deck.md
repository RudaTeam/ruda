# ADR-0019: Ввод: абстракция действий, геймпад и Steam Deck

- **Статус:** Предложено
- **Дата:** 2026-09-30
- **Связанные ADR:** 0004, 0005

## Контекст

Хотим полноценную игру на геймпаде и Steam Deck, а позже — сенсорное управление на мобильных.
Если с первого дня завязать логику на «клавишу W» и «клик мышью», поддержку других устройств
придётся вкручивать в каждый экран.

## Решение

**Действия вместо клавиш.** Игровая логика и UI получают действия: `Move` (ось 2D), `Look` (ось 2D),
`Jump`, `Attack`, `Use`, `Inventory`, `HotbarNext`… Привязки «устройство → действие» настраиваются
и переключаются по контекстам: игра, меню, инвентарь, чат.

**Устройства:** клавиатура и мышь (через winit); геймпады (через `gilrs` на Windows, Linux и macOS, с базой
раскладок SDL); позже — сенсорный ввод на мобильных как ещё одно устройство.

**Геймпад:** мёртвые зоны, кривые отклика стиков, настраиваемая чувствительность. Подсказки кнопок
переключаются на последнее использованное устройство: Xbox, PlayStation, Steam Deck, клавиатура.

**UI для геймпада.** Это ограничения для будущего UI-фреймворка:
- каждым экраном можно управлять фокусом: крестовина или стик, «подтвердить», «назад»;
- по инвентарю можно перемещаться между слотами (виртуальный курсор — опция);
- текст вводится с экранной клавиатуры (на Steam Deck — с системной клавиатуры Steam);
- интерфейс масштабируется, есть крупный шрифт: читаемость по критериям Steam Deck Verified (минимальная высота символа — около 9 px при 1280×800).

**Steam Deck** получает нативную Linux-сборку (ADR-0005), без Proton. Цель — статус Deck Verified.

## Последствия

**Плюсы:**
- Новое устройство — это новые привязки, а не правка игровой логики.
- У мобильного порта будет готовая основа для сенсорного управления.

**Минусы и риски:**
- Каждый экран UI нужно проектировать и тестировать и для мыши, и для геймпада.
- Steam Input может перехватывать геймпад и подменять раскладки. Тестировать нужно в обоих режимах.
